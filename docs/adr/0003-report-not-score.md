# ADR-0003：只报账，不打分

- 状态：已接受（2026-09-23）
- 相关：`DEVELOPMENT.md` §1 / §10 / §11

## 背景

屏幕时间工具几乎都会长出一个"效率分"：把应用按"生产性/非生产性"分类，算出今天的专注度，
给个 87 分，配一个红黄绿的进度环。

这个设计有几个问题：

1. **分类是主观的**。用 `code.exe` 写代码和生产 bug 都是"高效"；在 YouTube 上看教程和在 B 站刷视频
   在数据里完全一样。工具不知道你在干嘛，它只知道窗口标题。
2. **它把工具变成裁判**。用户开始为了分数好看而调数据（把某个应用加到白名单），
   账本就失真了 —— 而失真的账本没有任何用处。
3. **分数掩盖了不确定性**。这个工具的真实弱点（采样间隔、休眠断档、标题≠意图）用一个
   87 分的数字全糊住了，用户不会去读那些限定条件。

## 决策

**timetrace 只报事实，不做价值判断。**

具体到实现：

- 没有"效率分""专注指数""红黄绿"；没有应用分类表，不判断哪个应用"好"；
- 报告只回答四个问题：**每个应用占了多少时间、空闲多少、断档多少、最长连续段有多长**；
- 结构上强制诚实：所有桶加起来必须**等于**区间总长（守恒律，由测试钉住 §20-4），
  差额只能落在「空闲」与「未记录」这两个明说的桶里 —— **没有"其它"这种黑盒**；
- 报告头部主动自报可信度：覆盖率、最大采样间隔、丢弃的异常采样数；
- `--exclude` 的语义是"不算进前 N 名"，被排除的进程仍然单独列出时间，**不会从总账里消失**。

## 后果

- 用户拿到的是"账本"而不是"评分"，怎么做判断是他自己的事；
- 报告里那句"覆盖率只有 1.1%：区间内大部分时间没有记录，先确认 tracker 一直在跑，再相信下面的数字"
  比任何分数都有用；
- 产品少了一个最容易做的"亮点功能"，但这正是它和同类工具的区别。

## 备选方案

- **可配置的应用分类 + 效率分**：技术上很简单，但会把产品拉回"裁判"的位置，且必然引入
  "分数怎么算"的无穷争论；
- **"目标对比"（本周想在 code.exe 上 20 小时）**：这不是评分，是用户自己定的标尺 ——
  已放进里程碑 M2，且仍然只显示"离目标还差多少"，不给评价。
