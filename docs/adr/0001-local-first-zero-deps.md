# ADR-0001：本地优先 + 运行时零依赖

- 状态：已接受（2026-09-23）
- 相关：`DEVELOPMENT.md` §7 / §12 / §13 / §20-7

## 背景

屏幕时间工具天然要处理"人最敏感的数据"：你在用什么程序、几点在干什么、看的是什么文档。
市面上的同类工具多数要联网、要账号、把数据传到别人的服务器 —— 对一个"想知道自己时间去哪"
的工具来说，这个代价完全没必要。

同时它还有一个工程上的特殊要求：**它得开机就跑着**。装好一个 Python 包再建 venv 再激活，
对一个常驻小工具来说是过高的门槛；更糟的是，那条链路上任何一环坏掉（PATH、venv、依赖漂移），
结果都是"记录悄悄停了，而你几天后才发现"。

## 决策

1. **数据只在本机**：SQLite 单文件放在 `%LOCALAPPDATA%\timetrace`，没有服务端、没有账号、没有同步。
2. **运行时零依赖**：只用标准库 + `ctypes` 调 Win32。`pyproject.toml` 的 `dependencies = []`，
   并且闸门里有一条断言它保持为空。
3. **永不联网**，并且这句话是可验证的：验收脚本用 `ast` 扫 `src/timetrace/**` 的 import 图，
   出现 `socket` / `urllib` / `http` / `requests` / `httpx` 就判 FAIL（§20-7）。
4. **导出是一等公民**：`export --format json|csv [--no-titles]`，`purge` 真删（DELETE + VACUUM）。
   数据是你的，随时能拿走，也随时能毁掉。

## 后果

**正面**

- 装起来就是"解压 + `python -m timetrace track`"，没有 venv、没有依赖解析、没有供应链面；
- `pythonw.exe` 直接能跑，开机自启只需要启动目录里一个 `.cmd`；
- 审计面小到可以人肉读完：9 个模块、约 2600 行；
- 因为不联网，"这个工具会不会把我的浏览记录传走"这个问题可以被**验证**而不是被**相信**。

**负面与应对**

| 代价 | 应对 |
| --- | --- |
| 没有 `tqdm`/`rich`，console 表格要手写 | 一个 `pad()` + `display_width()`（CJK 占两列），20 行代码，还顺便解决了中文对齐 |
| 没有 `pywin32`，Win32 调用要写 ctypes 签名 | 集中在 `winapi.py` 一个文件；签名写错的经典坑（64 位下指针被截断）在注释里写明 |
| 只用标准库意味着不能用 `pendulum` 之类处理时区 | `time.mktime` 走操作系统时区规则（比 `tzinfo` 固定偏移更对，见 `timeutil.py` 的注释） |
| 手写 HTML/SVG 报告 | 单文件、可分享、零外部资源；顺便避免"报告要联网才能看" |

## 备选方案

- **`psutil` + `pywin32`**：写起来舒服，但为一个常驻工具引入两份二进制依赖不值；
- **C# / Rust 单文件 exe**：分发体验最好（无 Python），但开发与迭代成本高，且这个项目的价值
  在于数据口径而不是性能；
- **Electron/浏览器扩展**：拿不到真正的"前台窗口"，浏览器扩展只能看到标签页。
